# PayPal sandbox readiness

October 28, 2026. The adapter and 54 HTTP-mocked contract tests are implemented. No sandbox credentials are available, no provider operation was attempted, and T00 has not passed. Buyer approval for every order is the initial supported path. Saving a payment method and charging it later remain unverified and unimplemented.

## Account setup

1. Sign in to the [PayPal Developer Dashboard](https://developer.paypal.com/dashboard/), select **Sandbox**, open **Apps & Credentials**, and create a **Merchant** REST application linked to the controlled sandbox business account. Keep its client ID and secret on the server. [Official credential instructions](https://securepayments.paypal.com/us/cshelp/article/how-do-i-create-paypal-rest-api-credentials-ts1949).
2. Under **Testing Tools > Sandbox Accounts**, prepare separate business and personal test accounts. Use the personal sandbox account to approve purchases and the business account to inspect receipts and refunds. Find the controlled business account's PayPal merchant account ID for `PAYPAL_MERCHANT_ID`; this is the provider account ID, not `demo-merchant`, an email, or the REST app client ID. [Official sandbox account instructions](https://developer.paypal.com/api/get-started/).
3. Run the app with an HTTPS public callback endpoint. In the same sandbox app's **Sandbox Webhooks** section, register the backend's PayPal listener URL and record the resulting webhook ID. Subscribe to order approval and the capture pending, completed, denied, refunded, and reversed events supported by that app. The backend owner defines the listener route. [Official webhook setup](https://developer.paypal.com/payment-methods/webhooks/).
4. Set the following in the repository's untracked `.env` or deployment secret store. Set `PUBLIC_BASE_URL` to the actual frontend origin so callbacks return to the same app. Restart the API after changing settings. Never commit credentials or paste them into the UI, agent context, test fixtures, or evidence notes.

| Variable | Required value |
| --- | --- |
| `PAYPAL_ENV` | `sandbox` |
| `PAYPAL_BASE_URL` | `https://api-m.sandbox.paypal.com` |
| `PAYPAL_CLIENT_ID` | Sandbox REST app client ID |
| `PAYPAL_CLIENT_SECRET` | That app's sandbox secret |
| `PAYPAL_MERCHANT_ID` | Controlled business account's PayPal merchant ID |
| `PAYPAL_WEBHOOK_ID` | Webhook ID registered under that same sandbox app |
| `PUBLIC_BASE_URL` | Frontend origin; local default is `http://localhost:5173` |

`PAYPAL_ENVIRONMENT`, if also set, must equal `sandbox`. The adapter refuses every other API host and disables HTTP redirect following. The API uses the configured business as the payee for the internal `demo-merchant` catalog identity. Request bodies cannot replace that payee.

From `apps/api`, check environment readiness without making a provider request or printing values:

```powershell
python -c "from dotenv import load_dotenv; load_dotenv('../../.env'); from mandate.payments.paypal import missing_environment; print(missing_environment())"
```

An empty list means the four required values are present. It does not verify their validity, account permissions, endpoint reachability, or webhook registration.

## Integration contract

`mandate.payments.paypal.PayPalClient` accepts optional keyword settings `client_id`, `client_secret`, `merchant_id`, `webhook_id`, `base_url`, `trusted_merchant_id`, `http_client`, and `timeout`. Omitted provider settings read environment variables. The default timeout is 15 seconds per HTTP phase. `configured` requires client ID, secret, and merchant ID; `missing_environment()` also checks webhook ID and returns names only. Use one client per API process and close it with `aclose()` on shutdown. Injected HTTP clients remain caller-owned.

All provider methods are async and return provider JSON dictionaries:

```python
create_order(cart, request_id, return_url, cancel_url)
capture_order(order_id, request_id)
refund_capture(capture_id, amount_cents, request_id)
get_order(order_id)
get_capture(capture_id)
get_refund(refund_id)
verify_webhook(headers, event)
```

Cart items use the canonical `name`, `quantity`, `unit_price_cents`, and optional `merchant_id`. The cart requires `merchant_id`, `currency`, `total_cents`, and nonempty `items`. This initial catalog has no separate tax or shipping line: the item sum must equal the immutable total. Prices use integer arithmetic and exactly two USD decimal places. Caller approval URLs must come from trusted server configuration. The backend must support the provider's `payer-action` or `approve` link and bind callbacks to the stored order and original session. [Official create-order reference](https://developer.paypal.com/api/orders/v2/orders-create), [capture reference](https://developer.paypal.com/api/orders/v2/orders-capture).

Persist a different operation ID before each create, capture, or refund. Pass that ID unchanged as `request_id` for retries of the same payload. IDs accept 1 to 38 ASCII letters, digits, underscores, or hyphens, including normal UUIDs. The adapter performs no automatic mutation retries. The backend owns durable deduplication, bounded backoff, provider-retention decisions, and reservations. [Official idempotency rules](https://developer.paypal.com/api/rest/reference/idempotency/).

`PayPalError` exposes redacted `code`, `status_code`, `ambiguous`, and `retryable`. Transport failures, malformed financial responses, HTTP 408/409/425/429/5xx, unexpected redirects, and already-captured/refunded indications require reconciliation after mutation dispatch. OAuth failure happens before financial dispatch. A later definitive rejection cannot clear uncertainty left by an earlier attempt. Preserve unknown purchase/refund reservations until provider evidence resolves the operation. GET and signature-verification failures never establish financial failure.

`verify_webhook` returns the provider's `verification_status`. Only exact `SUCCESS` passes the signature check; `FAILURE`, missing headers, malformed responses, or outages do not. It forwards the original parsed event and case-insensitive transmission headers to PayPal, and does not fetch the supplied certificate URL itself. [Official verification reference](https://developer.paypal.com/api/webhooks/v1/verify-webhook-signature-post).

OAuth uses HTTP Basic client credentials, caches the token according to `expires_in` with an expiry margin, and serializes concurrent token acquisition. Refunds use the captured payment's ID and explicit USD amount. [Official authentication instructions](https://developer.paypal.com/api/get-started/), [partial-refund reference](https://developer.paypal.com/api/payments/v2/captures-refund).

## Local verification

From `apps/api`, run `python -m pytest tests/test_paypal.py -q`. The 54 passing cases use `httpx.MockTransport` only and cover trusted payee/amount payloads, unchanged retry IDs, OAuth caching/expiry, rejected inputs, provider outages, lost responses, signature success/failure, and readiness redaction. These checks establish the adapter contract, not provider feasibility.

## Deadline and working assumptions

Target submission is November 10 at 8:00 PM IST. The official cutoff is November 12, 2026 at 12:00 PM PST, which is November 13 at 1:30 AM IST. Keep the working project available through the December 15 judging close. [Official rules](https://paypalaihackathon.devpost.com/rules)

The schedule assumes one human builder can supervise 4-6 focused hours per day and up to three coding workers can run independently. It is a planning estimate, not a delivery guarantee. External account access and PayPal behavior are the main uncertainties. Each task should land as one or several small, independently reviewable changes.

## T00: prove the payment boundary first

Timebox the first investigation to half a focused day. The purpose is to learn whether this sandbox application supports the intended flow, not to build a general payments library.

1. Create the sandbox REST application, configure vaulting, create buyer and business test accounts, and register an HTTPS webhook endpoint.
2. Complete the documented buyer approval and initial order/capture flow. Wait for a usable saved method if vault creation is asynchronous.
3. Create a later order with the saved method and attempt capture without browser approval. Record whether any further payer action is required.
4. Refund part of that capture and confirm the provider result.
5. Receive and verify a webhook generated by the real sandbox operation. The simulator alone does not prove the full flow.
6. Save a redacted evidence note with accepted request shapes, account settings, order/capture/refund IDs, webhook event ID, and unresolved limitations. Keep secrets out of this note.

If vaulting remains blocked after checking the documented request shape and application permissions, choose buyer-present checkout for every order. Continue testing capture, refund, and webhooks. Update the UI and pitch to say "policy-controlled checkout with buyer approval." Do not call an ordinary approved order a reusable payment authorization.

If real sandbox capture and refund cannot be demonstrated, the payment gate has failed. Continue isolated policy/UI work only if useful, and resolve provider access before claiming the MVP works. A replay cannot replace this gate.

## Integration sequence

The critical path is T00/T01, then T02, T03, T06, T07, T08, and T09. T04 and T05 run alongside it once their contracts exist.

Integrate a narrow working purchase before adding recovery. Each merge must preserve that purchase flow. Shared contracts change through the coordinator, and a contract change must include updates to its consumers or an explicit compatibility period.

At the end of each work session, the task owner records the revision, changed behavior, checks and results, remaining failure, and next exact action. A task marked complete without evidence returns to review.

## Gates and scope reductions

| Trigger | Response |
| --- | --- |
| Vault flow not proven on Oct 29 | Select per-order approval; keep all policy and accounting requirements |
| First integrated capture not working by Nov 2 | Stop new feature work; fix T03 with policy and payment owners together |
| Behind schedule on Nov 4 | Cut Channel3, public SDK, MCP, elaborate animation, and optional grid functionality |
| Recovery blocked on Nov 5 | Keep one cause-review flow and one partial-refund path; remove extra case screens |
| Hosting uncertain on Nov 6 | Complete local run instructions and deployment selection immediately; do not depend on an expiring database |
| Validation fails after Nov 7 | Fix required failures and reduce presentation polish; do not weaken payment invariants |

Use a plain table if AG Grid integration consumes time. Use polling if resumable streaming delays delivery. Keep the audit trail even if its verification UI becomes a simple action. Never cut session isolation, stable retry identities, atomic reservation, human refund acceptance, or real sandbox evidence.

## Ready to release

Release requires the [validation checklist](06-validation-and-demo.md), a clean setup rehearsal, an identified operator, and an agreed hosting budget. Publishing and spending decisions belong to the human owner when the concrete build and costs are reviewable. This document schedules those decisions; it does not perform them.
